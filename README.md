
## M3 — Тест двох гравців
Для перевірки multiplayer та interpolation було запущено два вікна браузера, підключені до однієї кімнати. Кожне вікно представляло окремого гравця.
Тест проводився за таких мережевих умов:

latency: 100 ms;
jitter: ±30 ms;
packet loss: 2%;
server tick rate: 30 Hz;
interpolation delay: 100 ms.
Власний корабель відображається з останнього authoritative snapshot сервера, а віддалені кораблі буферизуються та відображаються через interpolation між отриманими snapshots.
Завдяки interpolation рух другого гравця залишається плавним навіть за наявності latency, jitter та втрати пакетів. При появі або зникненні entity клієнт також коректно обробляє різницю між snapshots.

Власні постріли використовують локальне prediction: куля створюється та відображається одразу після натискання Space. Після отримання відповідної authoritative кулі від сервера predicted bullet видаляється та замінюється серверною версією.

## M4 — Бінарний протокол та вимірювання

Гра підтримує два кодеки: JSON та бінарний кодек на основі `DataView`. Бінарний протокол використовує little-endian кодування, версію протоколу, ідентифікатори типів повідомлень та квантування кута.

### Вимірювання

Вимірювання виконані при **30 Hz** з використанням snapshot-фікстури для **4 гравців**.

| Кодек               | Байти/снапшот | KB/s на клієнт (down) | KB/s на клієнт (up) | Encode+decode, µs |
| ------------------- | ------------: | --------------------: | ------------------: | ----------------: |
| JSON                |           671 |                 19.66 |                2.96 |              3.21 |
| Binary (`DataView`) |           264 |                  7.73 |                0.21 |              8.07 |

Бінарний snapshot має значно менший розмір у мережі порівняно з JSON. У цьому Node.js benchmark час `encode+decode` для бінарного кодека виявився більшим, але мережеве навантаження є суттєво меншим.

### Round-trip тести

Бінарний кодек перевірено за допомогою round-trip тестів:

* для input-повідомлень `decode(encode(msg))` відповідає початковому повідомленню;
* для snapshot-повідомлень усі підтримувані поля зберігаються після кодування та декодування;
* значення з плаваючою крапкою використовують `Float32`, тому допускаються невеликі похибки;
* кути квантуються до 16 біт, тому після декодування можлива невелика похибка.

Результат тестів:

```text
INPUT round-trip: PASS
SNAPSHOT round-trip: PASS
RESULT: M4 BINARY CODEC TESTS PASS
```

### Бінарний протокол

Бінарні повідомлення містять:

* версію протоколу;
* тип повідомлення;
* sequence number та прапорці input для input-повідомлень;
* `roomId` та `lastProcessedSeq` для snapshot-повідомлень;
* розміри світу та рахунок;
* дані сутностей;
* опціональні поля сутностей, закодовані за допомогою прапорців;
* кути, закодовані як 16-бітні квантизовані значення.

Сервер може перемикатися між JSON та бінарним транспортом за допомогою змінної середовища `BINARY_PROTOCOL`.

## Netcode write-up

### 1. Основні проблеми мережевої гри

#### Затримка (latency)

Мережеві повідомлення не приходять миттєво: між відправленням input та отриманням snapshot є затримка. Через це керування без додаткових механізмів може відчуватися повільним.

Для зменшення впливу latency клієнт використовує **client-side prediction**. Клієнт не чекає на сервер для кожного input, а локально застосовує введення одразу. Кожен input має послідовний номер (`seq`), а сервер повертає `lastProcessedSeq` у snapshot. Це дозволяє клієнту визначати, які input вже були оброблені сервером.

#### Узгодженість стану (consistency)

Клієнт і сервер повинні приходити до однакового стану світу. Сервер є авторитетним джерелом стану гри, а snapshot містить актуальний стан світу та номер останнього обробленого input.

Client-side prediction покращує відчуття керування, але серверні snapshots залишаються джерелом істини. Після отримання snapshot клієнт може відкинути input, які сервер уже обробив, і повторно застосувати ті, що ще не були підтверджені.

Для плавного відображення стану також використовується інтерполяція snapshots. Вона додає невелику затримку відображення, але зменшує візуальні стрибки між мережевими оновленнями.

#### Читинг (cheating)

Клієнту не можна довіряти як джерелу істини для стану гри. Клієнт передає лише input, а сервер обробляє їх та оновлює авторитетний стан світу.

Таким чином, клієнт не визначає остаточні позиції, швидкості чи результати симуляції. Сервер надсилає snapshots, на основі яких клієнти синхронізують свій стан.

### 2. Netgraph та client-side prediction

До використання prediction затримка між введенням користувача та видимою реакцією гри була помітною, оскільки клієнт залежав від наступного серверного snapshot.

Після додавання client-side prediction локальний рух відбувається одразу після введення input. Netgraph дозволяє спостерігати мережеву затримку та різницю між локальним передбаченим станом і підтвердженим сервером станом.

Prediction не прибирає мережеву затримку фізично, але приховує її для локального керування. Серверні snapshots все одно потрібні для корекції та синхронізації стану.

### 3. Проблема детермінізму

Під час розробки виникла проблема, пов'язана з тим, що локальна клієнтська симуляція та серверна симуляція могли отримувати трохи різні результати.

Це показало важливість розділення відповідальності: клієнт може передбачати рух для плавного керування, але сервер залишається авторитетним джерелом стану.

Для синхронізації використовуються sequence numbers input та `lastProcessedSeq` у snapshots. Це дозволяє клієнту повторно застосовувати ще не підтверджені input після отримання серверного стану.

### 4. Інтерполяція та вибір затримки

Інтерполяція створює компроміс між плавністю та затримкою відображення.

Якщо використовувати дуже малу interpolation delay, клієнт має менше затримки, але частіше стикається з відсутністю наступного snapshot та може показувати ривки.

Більша interpolation delay дає більше snapshots для плавного переходу між станами, але збільшує затримку відображення.

Для гри обрано невелику interpolation delay, достатню для згладжування руху без створення зайвої затримки керування. Client-side prediction використовується окремо для локального гравця, щоб його керування залишалося швидким.

### Висновок

Архітектура netcode поєднує:

* **authoritative server** для узгодженого стану;
* **client-side prediction** для зменшення відчуття latency;
* **sequence numbers** для підтвердження input;
* **snapshots** для синхронізації стану;
* **interpolation** для плавного відображення віддалених об'єктів;
* **binary `DataView` protocol** для зменшення мережевого трафіку.
